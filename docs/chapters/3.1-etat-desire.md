# 3.1 — État désiré et architecture Kubernetes

## Ce que ce checkpoint ajoute

- `deploy/k8s/README.md` : création d'un cluster local k3d (1 serveur, 2 agents) ;
- `deploy/k8s/00-namespace.yaml` : le premier objet déclaré, le namespace `demo-fyc`.

On ne lance pas encore l'API : on observe comment Kubernetes stocke un état
désiré et le réconcilie.

## Lancer

```sh
k3d cluster create demo-fyc --agents 2 -p "8080:80@loadbalancer"
kubectl get nodes -o wide
kubectl get pods -n kube-system
kubectl apply -f deploy/k8s/00-namespace.yaml
```

## Observer

- `kubectl get nodes` : un nœud `server` (control plane) et deux `agent`.
- `kubectl get pods -n kube-system` : les composants du cluster (CoreDNS,
  Traefik, metrics-server, local-path-provisioner) sont eux-mêmes des Pods.
- `kubectl get namespace demo-fyc -o yaml` : l'objet stocké contient la
  déclaration (`spec`/`metadata`) et un `status` maintenu par le cluster.
- Réappliquer le même fichier : `unchanged`. `kubectl apply` décrit un état,
  pas une action ; le relancer est sans effet si rien n'a changé.
- `kubectl delete namespace demo-fyc` puis `kubectl apply` : l'état revient
  uniquement parce qu'il est déclaré dans un fichier versionné.
