# 3.3 — PostgreSQL opéré avec CloudNativePG

Le tag `3.3` ajoute `deploy/kubernetes/cloud/03-cloudnativepg.yaml`. Il remplace le Deployment PostgreSQL pédagogique du tag `2.2` par une ressource `Cluster` gérée par l'opérateur CloudNativePG.

## Prérequis

Installer une version vérifiée de l'opérateur dans le cluster cible, par exemple avec Helm :

```sh
helm repo add cloudnative-pg https://cloudnative-pg.github.io/charts
helm repo update
helm upgrade --install cnpg cloudnative-pg/cloudnative-pg \
  --namespace cnpg-system --create-namespace
```

En production, pinner la version du chart et lire les notes de compatibilité avant une mise à jour.

## Déployer le cluster

Ne pas appliquer simultanément `../local/01-db.yaml` et le manifeste CloudNativePG dans le même namespace : ils déclarent deux propriétaires différents pour PostgreSQL.

```sh
kubectl apply -f 03-cloudnativepg.yaml
kubectl get cluster -n demo-fyc
kubectl get pods -l cnpg.io/cluster=demo-fyc-db -n demo-fyc
```

CloudNativePG crée notamment un Service de lecture-écriture `demo-fyc-db-rw`. L'API doit alors utiliser `DB_HOST=demo-fyc-db-rw`, `DB_USER=app`, `DB_DATABASE=demo_fyc` et le mot de passe de `demo-fyc-db-app`. Le Deployment API du checkpoint `2.2` doit être adapté ou surchargé ; le module 4 fournit l'overlay Kustomize pour éviter une modification manuelle.

## Sauvegarde

Le `ScheduledBackup` est configuré avec une expression cron à six champs et la méthode `volumeSnapshot`. Il nécessite une `VolumeSnapshotClass` et un pilote CSI compatibles avec le cluster. Sans cette capacité, le cluster PostgreSQL peut fonctionner mais la sauvegarde échouera : vérifier les événements et ne pas présenter le TP comme une stratégie de reprise validée.

```sh
kubectl get scheduledbackup -n demo-fyc
kubectl describe scheduledbackup demo-fyc-db-daily -n demo-fyc
```

Les identifiants de démonstration sont des valeurs de laboratoire. Les sauvegardes réelles doivent être testées par une restauration et protégées par une politique de rétention.
