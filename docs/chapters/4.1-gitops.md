# 4.1 — Git comme source de vérité

## Ce que ce checkpoint ajoute

`.github/workflows/validate-manifests.yml` : à chaque pull request ou push sur
`main` qui touche `deploy/k8s/**` ou `gitops/**`, la CI valide les manifestes
avec [kubeconform](https://github.com/yannh/kubeconform) (mode `-strict`,
schémas Kubernetes 1.31). Un manifeste invalide est refusé avant d'atteindre
le cluster.

## Principes OpenGitOps

1. **Déclaratif** : l'état voulu est décrit (`deploy/k8s/`), pas scripté.
2. **Versionné et immuable** : cet état vit dans Git, avec historique et revue.
3. **Tiré automatiquement** : un agent dans le cluster récupère l'état depuis Git.
4. **Réconcilié en continu** : l'agent corrige tout écart entre Git et le cluster.

**Push** : la CI exécute `kubectl apply` et détient les accès au cluster.
**Pull** : un agent dans le cluster (Argo CD, chapitre 4.2) lit Git ; la CI
ne fait que valider et publier des images.

## Lancer

Reproduire la validation en local :

```sh
docker run --rm -v "$PWD:/repo" -w /repo ghcr.io/yannh/kubeconform:v0.7.0 \
  -strict -summary -ignore-missing-schemas -kubernetes-version 1.31.0 deploy/k8s
```

## Observer

- Ajouter un champ inconnu (ex. `replica: 3`) dans `04-api.yaml` : kubeconform
  échoue avec `additional properties 'replica' not allowed`.
- Ouvrir une pull request avec cette erreur : le check `kubeconform` est rouge.
- Corriger, pousser : le check repasse au vert. Seul ce qui est validé et
  fusionné dans `main` a vocation à atteindre le cluster.
