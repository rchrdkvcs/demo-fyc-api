# 4.3 — Cas pratique : livrer une nouvelle version

## Énoncé

Ajouter une route `GET /version` qui renvoie `{ "version": "<APP_VERSION>" }`,
où `APP_VERSION` est une variable d'environnement (`"dev"` si elle est absente).

La livrer jusqu'au cluster **uniquement via Git**, sans `kubectl apply` ni
`kubectl set image` :

commit → tag → image GHCR (CI) → mise à jour du tag d'image dans `deploy/k8s/`
→ synchronisation Argo CD → vérification `curl /version`.

Point de départ : tag `4.2` sur un fork, Application Argo CD pointant vers ce fork.

## Ce que ce checkpoint ajoute (corrigé)

- `app/controllers/version_controller.ts` et la route `GET /version` ;
- `APP_VERSION` optionnelle dans `start/env.ts` ;
- `tests/functional/version.spec.ts` ;
- `deploy/k8s/02-config.yaml` : `APP_VERSION: '4.3'` ;
- `deploy/k8s/03-migration-job.yaml` et `04-api.yaml` : image `ghcr.io/rchrdkvcs/demo-fyc-api:4.3`.

## Étapes de correction

1. **Code et test, en local**

   ```sh
   pnpm test
   APP_VERSION=local pnpm dev
   curl http://localhost:3333/version      # {"version":"local"}
   ```

2. **Commit et tag** : le tag déclenche `publish-image.yml`.

   ```sh
   git add app start tests
   git commit -m "feat: add /version endpoint"
   git tag -a 4.3 -m "Cas pratique"
   git push origin main 4.3
   ```

3. **Image** : attendre la fin du workflow dans l'onglet *Actions*, puis vérifier
   `docker pull ghcr.io/<compte>/demo-fyc-api:4.3`.

4. **Manifestes** : dans `deploy/k8s/`, passer l'image de `2.1` à `4.3`
   dans `03-migration-job.yaml` et `04-api.yaml`, ajouter `APP_VERSION: '4.3'`
   dans la ConfigMap, valider puis pousser.

   ```sh
   docker run --rm -v "$PWD:/repo" -w /repo ghcr.io/yannh/kubeconform:v0.7.0 \
     -strict -summary -ignore-missing-schemas deploy/k8s
   git commit -am "deploy: release 4.3"
   git push origin main
   ```

5. **Synchronisation** : dans Argo CD, **Refresh** puis observer le rolling update
   (`kubectl get pods -n demo-fyc -w`). Le Job de migration est rejoué.

6. **Vérification**

   ```sh
   curl http://api.localhost:8080/version  # {"version":"4.3"}
   ```

## Points d'attention

- Modifier une ConfigMap ne redémarre pas les Pods : ici le changement d'image
  déclenche le rolling update, qui relit la ConfigMap. Changer seulement
  `APP_VERSION` ne suffirait pas.
- Pousser les manifestes **avant** que l'image existe donne `ImagePullBackOff` ;
  avec `maxUnavailable: 0`, les anciens Pods continuent de servir le trafic.
- Le tag Git, le tag d'image et `APP_VERSION` portent la même valeur : c'est ce
  qui rend la version observable de bout en bout.
