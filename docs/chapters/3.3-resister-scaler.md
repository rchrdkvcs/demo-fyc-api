# 3.3 — Résister et scaler

## Ce que ce checkpoint ajoute

- `04-api.yaml` : `resources.requests` / `limits`, stratégie `RollingUpdate`
  avec `maxUnavailable: 0` et `maxSurge: 1` ; le champ `replicas` est retiré
  car le HPA en devient responsable ;
- `01-db.yaml` : `requests` / `limits` pour PostgreSQL ;
- `06-hpa.yaml` : HorizontalPodAutoscaler `autoscaling/v2`, 2 à 5 réplicas,
  cible 60 % de CPU (par rapport aux `requests`).

k3d fournit metrics-server : le HPA fonctionne sans installation supplémentaire.

## Lancer

```sh
kubectl apply -f deploy/k8s/
kubectl get hpa -n demo-fyc
kubectl top pods -n demo-fyc
```

## Observer (TP3)

**Self-healing**

```sh
kubectl delete pod -n demo-fyc -l app=demo-fyc-api --wait=false
kubectl get pods -n demo-fyc -w     # de nouveaux Pods remplacent les anciens
```

**Rolling update**

```sh
kubectl set image deployment/demo-fyc-api -n demo-fyc api=ghcr.io/rchrdkvcs/demo-fyc-api:3.2
kubectl rollout status deployment/demo-fyc-api -n demo-fyc
kubectl rollout undo deployment/demo-fyc-api -n demo-fyc
```

Pendant le déploiement, une boucle `curl` sur `http://api.localhost:8080/ready`
ne doit voir aucune erreur : un ancien Pod n'est retiré qu'une fois le nouveau prêt.

**Autoscaling**

```sh
kubectl run load -n demo-fyc --rm -it --image=busybox:1.36 --restart=Never -- \
  sh -c 'while true; do wget -q -O- http://demo-fyc-api:3333/api/tweets >/dev/null; done'
kubectl get hpa demo-fyc-api -n demo-fyc -w   # dans un autre terminal
```

La colonne `TARGETS` dépasse 60 %, `REPLICAS` monte jusqu'à 5. Après l'arrêt
de la charge, le HPA redescend à 2 au bout de la fenêtre de stabilisation (2 min).
