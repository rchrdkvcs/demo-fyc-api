# 3.2 — Déployer l'API sur k3d

## Ce que ce checkpoint ajoute

Les manifestes de la stack complète dans `deploy/k8s/` :

- `01-db.yaml` : PostgreSQL avec un **PVC** (volume `local-path` fourni par k3d) ;
- `02-config.yaml` : **ConfigMap** (configuration non sensible) et **Secret** (identifiants) ;
- `03-migration-job.yaml` : **Job** de migration, séparé du démarrage de l'API ;
- `04-api.yaml` : **Deployment** à 2 réplicas avec **probes** et **Service** ClusterIP ;
- `05-ingress.yaml` : **Ingress** Traefik sur `api.localhost`.

L'image est celle publiée au chapitre 2.1 : `ghcr.io/rchrdkvcs/demo-fyc-api:2.1`.

## Lancer

```sh
kubectl apply -f deploy/k8s/
kubectl get pods -n demo-fyc -w
curl -i http://api.localhost:8080/ready
curl -X POST http://api.localhost:8080/api/tweets \
  -H 'Content-Type: application/json' -d '{"content":"depuis k3d"}'
```

## Observer

- `kubectl get pvc -n demo-fyc` : le volume est `Bound`.
- `kubectl logs job/demo-fyc-migrate -n demo-fyc` : la migration a tourné une fois.
- `kubectl get endpoints demo-fyc-api -n demo-fyc` : deux IP de Pods derrière le Service.
- `kubectl scale deployment/demo-fyc-db -n demo-fyc --replicas=0` : `/ready`
  échoue, les Pods API passent `0/1 READY` et sortent du Service, sans redémarrer.
  Remettre `--replicas=1` : ils reviennent seuls, les tweets sont toujours là (PVC).
- `kubectl describe pod -n demo-fyc -l app=demo-fyc-api` : section `Events`.
