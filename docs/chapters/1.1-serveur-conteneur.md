# 1.1 — Du serveur au conteneur

## Ce que ce checkpoint ajoute

- la route `GET /ready`, qui exécute `select 1` sur PostgreSQL et renvoie `503` si la base ne répond pas ;
- la documentation du parcours (`README.md`, `docs/repository-map.md`).

`/health` dit « le processus tourne », `/ready` dit « il peut servir des requêtes ».
Cette distinction servira aux healthchecks Compose (1.3) puis aux probes Kubernetes (3.2).

## Lancer

```sh
pnpm install --frozen-lockfile
cp .env.example .env
node ace generate:key
node ace migration:run
pnpm dev
```

## Observer

```sh
curl -i http://localhost:3333/health   # 200
curl -i http://localhost:3333/ready    # 200 si PostgreSQL répond
```

Arrêter PostgreSQL puis relancer les deux commandes : `/health` reste à `200`,
`/ready` passe à `503`. L'application dépend d'un service externe : c'est ce
couple API + base qu'on va déplacer d'un poste vers un serveur, puis vers un cluster.
